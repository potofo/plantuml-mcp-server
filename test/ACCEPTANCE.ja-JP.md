# 受け入れ要件(EARS形式)

PlantUML MCP Server の受け入れ要件です。
[Docker MCP Catalog の受け入れ基準](https://github.com/docker/mcp-registry/blob/main/CONTRIBUTING.md)
と、本プロジェクト固有の機能要件から導出しています。

各要件は EARS(Easy Approach to Requirements Syntax)で記述し、安定した
ID を付与しています。「自動」と記載した要件は
[`acceptance-test.sh`](acceptance-test.sh) が検証します。CI は同一
ワークフロー内でビルドしたイメージに対してこのスクリプトを実行します
([`.github/workflows/ci.yml`](../.github/workflows/ci.yml) 参照)。
スクリプトは要件 ID ごとに TAP 形式の `ok` / `not ok` を 1 行ずつ
出力するため、CI が失敗した場合はどの要件に違反したかが特定できます。

英語版: [ACCEPTANCE.md](ACCEPTANCE.md)

## 使用する EARS パターン

| パターン | テンプレート |
| --- | --- |
| 普遍(Ubiquitous) | 〈システム〉は〈応答〉しなければならない。 |
| イベント駆動(Event-driven) | 〈トリガー〉のとき、〈システム〉は〈応答〉しなければならない。 |
| 状態駆動(State-driven) | 〈状態〉の間、〈システム〉は〈応答〉しなければならない。 |
| 望ましくない挙動(Unwanted behavior) | もし〈条件〉ならば、〈システム〉は〈応答〉しなければならない。 |

## 1. Docker MCP Catalog 適合要件(REQ-CAT)

| ID | パターン | 要件 | 検証方法 |
| --- | --- | --- | --- |
| REQ-CAT-001 | 普遍 | プロジェクトは MIT ライセンスで提供され、リポジトリルートの `LICENSE.txt` にライセンス全文を含まなければならない。 | 自動 |
| REQ-CAT-002 | 普遍 | リポジトリは docker/mcp-registry 形式の `server.yaml` を提供し、`name`・`type`・`meta.category`・`about.title`・`about.icon`・`about.description`・`source.project` を含まなければならない。 | 自動 |
| REQ-CAT-003 | 普遍 | リポジトリはルートに `Dockerfile` を提供し、そこからコンテナイメージがビルドできなければならない。 | 自動(CI の `docker build` ステップ) |
| REQ-CAT-004 | 普遍 | コンテナは非 root ユーザーで動作しなければならない。 | 自動 |
| REQ-CAT-005 | イベント駆動 | MCP クライアントが stdio 経由で `initialize` を送信したとき、サーバーは自身を `plantuml-mcp` として識別する成功応答を返さなければならない。 | 自動 |
| REQ-CAT-006 | イベント駆動 | MCP クライアントが事前の設定・シークレット・環境変数なしに `tools/list` を要求したとき、サーバーはちょうど `render_svg` と `render_png` の 2 ツールを、それぞれ JSON Schema の入力定義付きで列挙しなければならない。 | 自動 |
| REQ-CAT-007 | 普遍 | リリースイメージは `linux/amd64` と `linux/arm64` 向けに publish され、リリース時に生成される `catalog.yaml` から digest で参照されなければならない。 | `release.yml` とリリース実行結果のレビュー |
| REQ-CAT-008 | 状態駆動 | URL `!include` を使用しないダイアグラムをレンダリングしている間、サーバーは外向きネットワークアクセスを必要としてはならない。 | 自動(テストコンテナを `--network none` で実行) |

## 2. 機能要件(REQ-FUN)

| ID | パターン | 要件 | 検証方法 |
| --- | --- | --- | --- |
| REQ-FUN-001 | イベント駆動 | 有効な PlantUML ソースで `render_svg` が呼び出されたとき、サーバーはレンダリング済み SVG を MIME タイプ `image/svg+xml` の埋め込みリソースとして短いステータステキストと共に返し、SVG テキストをテキストコンテンツにインライン展開してはならない。 | 自動 |
| REQ-FUN-002 | イベント駆動 | 有効な PlantUML ソースで `render_png` が呼び出されたとき、サーバーは有効な PNG を MIME タイプ `image/png` の画像コンテンツとして返さなければならない。 | 自動 |
| REQ-FUN-003 | イベント駆動 | ソースが Graphviz レイアウトを必要とするとき(例: クラス図)、サーバーはイメージに同梱された Graphviz を用いてレンダリングしなければならない。 | 自動 |
| REQ-FUN-004 | イベント駆動 | ソースが CJK(例: 日本語)ラベルを含むとき、サーバーは同梱の Noto CJK フォントでレンダリングし、ラベルが出力に現れなければならない。 | 自動 |
| REQ-FUN-005 | 普遍 | すべてのツールの description は、呼び出し元 LLM がそのリリースに有効な構文を書けるよう、PlantUML レンダラーの正確なバージョンを明示しなければならない。 | 自動 |

## 3. エラー処理 — 望ましくない挙動(REQ-ERR)

| ID | パターン | 要件 | 検証方法 |
| --- | --- | --- | --- |
| REQ-ERR-001 | 望ましくない挙動 | もし `source` 引数が欠落・空・空白のみならば、サーバーは非空文字列が必要である旨のツールエラー(`isError: true`)を返さなければならない。 | 自動 |
| REQ-ERR-002 | 望ましくない挙動 | もしソースが 100,000 文字を超えるならば、サーバーは上限を明示したツールエラーを返さなければならない。 | 自動 |
| REQ-ERR-003 | 望ましくない挙動 | もしソースに PlantUML 構文エラーが含まれるならば、サーバーは「syntax error」の文言と該当行番号を含むツールエラーを返さなければならない。 | 自動 |
| REQ-ERR-004 | 望ましくない挙動 | もしソースに複数の `@startuml` ブロックが含まれるならば、サーバーは 1 回の呼び出しにつきちょうど 1 ブロックを送るよう指示するツールエラーを返さなければならない。 | 自動 |
| REQ-ERR-005 | 望ましくない挙動 | もし MIT ビルドに含まれない機能(例: ditaa)が要求されたならば、サーバーは終了せずに応答しなければならない — ツールエラー、または機能が利用不可である旨をレンダリングした画像のいずれかを返す。 | 自動 |
| REQ-ERR-006 | 望ましくない挙動 | もしレンダリングが 60 秒以内に完了しないならば、サーバーはレンダリングを中断しタイムアウトエラーを返さなければならない。 | 設計レビュー+コード検査(`PlantUmlRenderer`) |

## 4. 運用要件(REQ-OPS)

| ID | パターン | 要件 | 検証方法 |
| --- | --- | --- | --- |
| REQ-OPS-001 | 状態駆動 | 稼働中、サーバーは stdout に JSON-RPC プロトコルメッセージのみを書き込み、診断ログは stderr に出力しなければならない。 | 自動(stdout の全行が JSON としてパースできること) |
| REQ-OPS-002 | イベント駆動 | コンテナが SIGTERM を受信したとき(例: ゲートウェイによる停止)、サーバーは 10 秒以内にシャットダウンしなければならない。 | 自動 |
| REQ-OPS-003 | イベント駆動 | ツール呼び出しがエラーを返した後も、サーバーは後続のリクエストを処理し続けなければならない。 | 自動 |
| REQ-OPS-004 | イベント駆動 | 複数のツール呼び出しが同時に進行しているとき、サーバーはそのすべてに応答しなければならない(デッドロックやリクエスト喪失がないこと)。 | 自動(テストセッションは全リクエストを一括送信)+ユニットテスト |

## 自動検証の実行方法

ローカルでの実行(イメージが存在すること。タグは任意):

```bash
docker build -t plantuml-mcp:ci .
IMAGE=plantuml-mcp:ci bash test/acceptance-test.sh
```

スクリプトで検証しない要件(REQ-CAT-007、REQ-ERR-006)は、代替の
検証方法を付記した `# SKIP` 行として出力されるため、TAP 出力には
常にすべての要件 ID が現れます。

## テスト結果の所在

- **[RESULTS.md](RESULTS.md)** — スクリプトの実行のたびに再生成される
  Markdown サマリ(日時・イメージ・コミット・要件別の結果表)。
  リポジトリにコミットされているものは直近の検証実行のスナップショット。
- **CI アーティファクト `test-results`** — CI 実行のたびに生の TAP 出力
  (`acceptance-tap.txt`)と `RESULTS.md` をアップロード。ステップが
  失敗した場合も、実行の Summary ページからダウンロードできます。

依存: `bash`・`docker`・`jq`・`base64`・`od`
(いずれも GitHub `ubuntu-latest` ランナーに標準搭載)。
